# F1 — Migration Hub Application Grouping Issues

## Symptoms
- Can't create application group
- Servers not appearing in group
- Group status incorrect

## Triage Commands

```bash
aws mgh list-migration-tasks --max-results 20
aws mgh list-discovered-resources --migration-task-name <task> --progress-update-stream <stream>
aws discovery list-configurations --configuration-type SERVER --max-results 20
```

## Common Causes

1. **Server not discovered** — Server must be in discovery data first
2. **Wrong resource identifier** — Using wrong ID format for server
3. **Home region mismatch** — Grouping only works in home region
4. **Duplicate grouping** — Server already in another application
5. **Discovery data stale** — Server data not refreshed

## Resolution

- Verify server exists in discovery data
- Associate resources: `aws mgh associate-discovered-resource --migration-task-name <task> --progress-update-stream <stream> --discovered-resource ConfigurationId=<server-id>`
- Work in home region for all grouping operations
- Use Migration Hub console for visual application grouping
- Refresh discovery data if servers are missing

## Escalation Conditions

- **Escalate immediately** if the issue involves potential data loss or corruption
- **Escalate immediately** if a production workload is impacted and cannot be restored within the agreed SLA
- **Escalate immediately** if the root cause is unclear after initial diagnostic steps are exhausted
- **Escalate to service team** if the issue appears to be a platform-level bug or undocumented behavior
- **Escalate to security team** if unauthorized access, policy violations, or credential exposure is suspected

## Data Sensitivity

- Verify data classification before performing any read or export operations
- Ensure all troubleshooting outputs (logs, configurations, snapshots) are handled according to the customer's data handling policy
- Mask or redact personally identifiable information (PII) in all shared diagnostics
- Do not copy production data to non-production environments without explicit authorization
- Retain troubleshooting artifacts only for the duration required and dispose of them securely

## Prohibited Actions

- **NEVER** delete migration tasks or application groupings that are actively tracking in-progress migrations
- **NEVER** change the home region setting without understanding the impact on all integrated migration tools
- **NEVER** remove discovery agent data or imported server records without confirming migration planning is complete
- **NEVER** modify Refactor Spaces routing configurations on production environments without a rollback plan
- **NEVER** override strategy recommendations without documenting the business justification

## Phase 3 � Rollback

1. **Identify rollback trigger**: Determine if the applied change has caused degradation, unexpected behavior, or failed validation checks
2. **Preserve current state**: Capture logs, configuration snapshots, and resource states before initiating rollback
3. **Execute rollback steps**: Revert configuration changes in reverse order of application, verifying each step
4. **Validate service recovery**: Confirm that the service has returned to its pre-change operational state using health checks and functional tests
5. **Document rollback**: Record the rollback trigger, steps taken, time to recovery, and any residual issues for post-incident review
