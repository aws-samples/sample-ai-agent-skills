## Phase 1 — Triage

MUST:
- Review the template for auto-generated IAM policies: `grep -A 10 'Policies:' template.yaml`
- Check environment variables generated by connections: `grep -A 10 'Environment:' template.yaml`
- Validate the template after connection changes: `sam validate --template-file template.yaml --lint`

SHOULD:
- Verify both resources support the connection type
- Check for circular dependencies between connected resources

MAY:
- Review the CloudFormation dependency graph: `aws cloudformation describe-stack-resources --stack-name <name>`

## Phase 2 — Remediate

MUST:
- Manually clean up orphaned IAM policies after removing connections
- Remove stale environment variables from disconnected resources
- Fix circular dependency errors by restructuring connections

SHOULD:
- Validate IAM policies are correct for the connection type
- Test connections with minimal permissions first

MAY:
- Use Ref and GetAtt intrinsic functions for custom connections
- Document connection-generated artifacts for team awareness

## Safety Ratings

```
safety_ratings:
  - "grep template.yaml: GREEN — read-only template inspection"

  - "manual IAM policy editing: YELLOW — modifies security configuration"
```

## Escalation Conditions

- Connections generate incorrect IAM permissions that grant excessive access
- Circular dependencies cannot be resolved through connection restructuring
- Connection artifacts persist after multiple cleanup attempts
- Auto-generated policies conflict with organization SCPs

## Data Sensitivity

- `grep template.yaml`: MEDIUM — may reveal IAM policies and resource ARNs
- `aws cloudformation describe-stack-resources`: MEDIUM — reveals stack resource details
- IAM policy content: HIGH — reveals permission boundaries and access patterns

## Prohibited Actions

- NEVER assume removing a canvas connection cleans up IAM policies automatically
- NEVER add wildcard (*) IAM permissions to fix connection issues
- NEVER modify IAM policies in production without change set review
- NEVER create connections that grant cross-account access without explicit approval

## Phase 3 — Rollback

1. Restore template from version control to undo connection changes: `git checkout -- template.yaml`
2. If IAM policies were manually modified, restore from the pre-change template
3. Verify no orphaned environment variables remain: `grep 'Environment:' template.yaml`
4. Validate the restored template: `sam validate --template-file template.yaml --lint`
5. Review IAM policies to ensure no excessive permissions remain from connection artifacts

## Common Issues

- symptoms: "Lambda function cannot access DynamoDB table after creating a connection"
  diagnosis: "Connection may not have generated the correct IAM policy or environment variable."
  resolution: "Check the generated IAM policy includes dynamodb:* actions for the table ARN and the TABLE_NAME environment variable is set."
