## Phase 1 — Triage

MUST:
- Validate the template: `aws cloudformation validate-template --template-body file://template.yaml`
- Check for resource limit violations: `grep -c 'Type: AWS::' template.yaml`
- Review recent stack events for errors: `aws cloudformation describe-stack-events --stack-name <name> --query 'StackEvents[?ResourceStatus==`CREATE_FAILED`].[LogicalResourceId,ResourceStatusReason]'`

SHOULD:
- Check template size: `wc -c template.yaml` (limit: 51,200 bytes direct, 1 MB via S3)
- Verify all referenced parameters have values

MAY:
- Create a change set to preview changes: `aws cloudformation create-change-set --stack-name <name> --template-body file://template.yaml --change-set-name preview`
- Check for drift: `aws cloudformation detect-stack-drift --stack-name <name>`

## Phase 2 — Remediate

MUST:
- Fix template syntax errors identified by validation
- Resolve resource dependency issues (DependsOn, Ref, GetAtt)
- Ensure all required resource properties are present

SHOULD:
- Use change sets before applying updates to production stacks
- Upload large templates to S3: `aws s3 cp template.yaml s3://<bucket>/template.yaml`

MAY:
- Split large templates into nested stacks
- Use CloudFormation linter (cfn-lint) for detailed validation: `cfn-lint template.yaml`

safety_ratings:

## Escalation Conditions

- Template validation passes but stack creation fails with internal CloudFormation errors
- Stack is stuck in UPDATE_ROLLBACK_FAILED state
- Template exceeds CloudFormation resource limits (500 resources)
- Cross-stack references are broken after template changes

## Data Sensitivity

- `aws cloudformation validate-template`: LOW — validates syntax only
- `aws cloudformation describe-stack-events`: MEDIUM — reveals resource creation details and error messages
- `aws cloudformation create-change-set`: MEDIUM — reveals planned infrastructure changes

## Prohibited Actions

- NEVER execute a change set in production without reviewing it first
- NEVER delete a stack to fix template errors if it contains stateful resources
- NEVER use --disable-rollback in production deployments
- NEVER modify template logical resource IDs as this causes resource replacement

## Phase 3 — Rollback

1. If a stack update failed, check rollback status: `aws cloudformation describe-stacks --stack-name <name> --query 'Stacks[0].StackStatus'`
2. For UPDATE_ROLLBACK_FAILED, continue rollback: `aws cloudformation continue-update-rollback --stack-name <name>`
3. Restore the previous template version from version control
4. Delete failed change sets: `aws cloudformation delete-change-set --stack-name <name> --change-set-name preview`
5. Verify stack is in a stable state before retrying

## Common Issues

- symptoms: "Stack creation fails with 'Circular dependency between resources'"
  diagnosis: "Application Composer connections may create circular Ref/GetAtt dependencies."
  resolution: "Review resource dependencies and break the cycle by using SSM parameters or removing one connection direction."
