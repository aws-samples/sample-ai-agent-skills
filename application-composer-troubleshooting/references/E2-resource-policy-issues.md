## Phase 1 — Triage

MUST:
- Review auto-generated IAM policies in the template: `grep -A 20 'Policies:' template.yaml`
- Check Lambda execution role permissions: `aws iam get-role-policy --role-name <role-name> --policy-name <policy-name>`
- Verify the function can access connected resources: `aws lambda invoke --function-name <name> --payload '{}' output.json && cat output.json`

SHOULD:
- Check for SCP restrictions: `aws organizations list-policies --filter SERVICE_CONTROL_POLICY`
- Review resource-based policies on target resources (S3, SQS, SNS)

MAY:
- Use IAM Policy Simulator: `aws iam simulate-principal-policy --policy-source-arn <role-arn> --action-names <action>`
- Check CloudTrail for AccessDenied events: `aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=<api-call> --max-results 10`

## Phase 2 — Remediate

MUST:
- Fix insufficient IAM permissions in the template
- Remove overly permissive wildcard policies generated by connections
- Ensure resource ARNs in policies match actual resource ARNs

SHOULD:
- Apply least-privilege principle to auto-generated policies
- Use SAM policy templates for common patterns: `AWS::Serverless::Function Policies: - DynamoDBCrudPolicy`

MAY:
- Implement resource-based policies for cross-account access
- Set up IAM Access Analyzer to monitor policy effectiveness

## Escalation Conditions

- Auto-generated policies grant public access to resources
- IAM policies conflict with organization SCPs
- Cross-account access policies require security team approval
- Resource policies expose sensitive data to unintended principals

## Data Sensitivity

- `aws iam get-role-policy`: HIGH — reveals IAM permission details
- `aws lambda invoke`: HIGH — executes function code that may access sensitive data
- `aws cloudtrail lookup-events`: MEDIUM — reveals API call patterns and principals
- Template IAM policies: HIGH — reveals access control configuration

## Prohibited Actions

- NEVER add wildcard (*) resource or action permissions to fix access issues
- NEVER modify IAM policies in production without change set review
- NEVER grant cross-account access without explicit security team approval
- NEVER remove resource-based policies without understanding their purpose

## Phase 3 — Rollback

1. Restore IAM policies from the previous template version: `git checkout -- template.yaml`
2. If inline policies were modified directly, restore from CloudFormation: `aws cloudformation update-stack --stack-name <name> --use-previous-template`
3. Verify no excessive permissions remain: `aws iam simulate-principal-policy --policy-source-arn <arn> --action-names s3:* dynamodb:*`
4. Check resource-based policies were not inadvertently modified
5. Audit IAM changes with CloudTrail

## Common Issues

- symptoms: "Lambda function returns AccessDeniedException when accessing DynamoDB"
  diagnosis: "Auto-generated IAM policy may not include the required DynamoDB actions or the table ARN is incorrect."
  resolution: "Check the Policies section in the SAM template. Ensure the DynamoDB table ARN matches and required actions (GetItem, PutItem, etc.) are included."
